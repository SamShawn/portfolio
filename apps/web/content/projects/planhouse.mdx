## 背景与目标

PlanHouse 是微信小程序端的活动平台，累计 20 万+ 用户、8,000+ 场线下活动。用户在小程序内浏览活动、报名参与、查看社群信息，平台侧负责活动发布与管理。

我负责小程序端全部前端 UI 界面的开发与迭代维护。

## 我的角色与范围

前端程序员，负责小程序端 UI 开发与迭代。技术栈为 React + Taro。

具体范围包括：活动发布、报名、社群展示等核心功能的前端开发，与产品、后端协作完成功能从需求到上线，以及组件复用和多端适配等工程实践。

## 技术栈与架构取舍

- **React + Taro**：用 Taro 而非原生小程序开发，是为了用 React 的组件模型组织页面，同时保留未来向 H5 复用的可能。
- **组件复用优先**：活动卡片、报名表单这类高频 UI 抽成通用组件，避免每个页面重复实现。代价是组件需要预留足够的 props 扩展点，过度抽象反而会增加维护成本。

## 关键难点

### 难点一：高频 UI 的组件复用

**问题**：活动列表、活动详情、报名页等多个页面都包含活动卡片和报名表单，早期各页面各自实现，样式和行为不一致，改一处要改多处。

**方案**：抽取活动卡片和报名表单为通用组件，各页面通过 props 传入数据和回调，样式差异用有限的变体参数控制。

**取舍**：为什么不直接用一套组件覆盖所有场景？不同页面对卡片的信息密度和交互要求不同，强行统一会导致组件 props 膨胀。选择“通用结构 + 有限变体”的方式，复用高频部分，保留页面级的组合空间。代价是变体参数需要克制，否则组件会退化成配置地狱。

**结果**：高频 UI 在多页面间保持一致，修改只需改组件一处。

### 难点二：多端适配

**问题**：小程序在不同机型和系统版本上存在样式和安全区差异，尤其是底部操作区和弹窗在部分机型上被遮挡。

**方案**：用 Taro 提供的适配能力处理尺寸单位，针对安全区做单独处理，关键交互区域预留足够的触控尺寸。

**取舍**：为什么不做全量机型适配？覆盖所有机型成本过高，收益递减。优先保证主流机型和系统版本的核心流程可用，边缘机型依赖 Taro 的兜底能力。代价是少数边缘机型仍可能有细微差异，需要在反馈中迭代修复。

**结果**：主流机型上核心流程的布局和交互正常。

## 结果与链接

- 参与活动发布、报名、社群展示等功能从需求到上线，覆盖 8,000+ 场活动场景
- 组件复用减少重复实现，多端适配保证主流机型可用

## 如果重做

- 会在组件抽取前先梳理各页面的真实差异，避免抽象过早导致 props 膨胀
- 会为多端适配建立一份机型清单和验收流程，而不是依赖上线后反馈
- 会把高频组件的样式变体收敛为设计 token，减少页面间的样式漂移
