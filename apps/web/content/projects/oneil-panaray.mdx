## 背景与目标

PANARAY® 是面向机构投资者的全球股票研究平台，覆盖 82,000+ 证券、70+ 国家市场。产品承载 5,000+ 量化因子与 Datagraph 可视化，用户需要在同一终端里完成筛选、对比、下钻的研究流程。

我所在团队负责平台的前端交付与部分后端接口维护，我主要承担数据可视化模块。

## 我的角色与范围

全栈程序员，负责数据可视化模块的前后端开发与维护。技术栈为 React + Python + PostgreSQL。

具体范围包括：可视化功能从交互稿到接口的独立交付、大数据量图表渲染的性能处理、多市场数据格式的适配，以及参与需求评审与技术方案设计、Git 协作和线上问题排查。

## 技术栈与架构取舍

- **前端 React**：机构级终端交互密集，React 的组件模型适合把图表、筛选器、数据面板拆成可独立迭代的单元。
- **后端 Python + PostgreSQL**：产品侧已有成熟的数据处理链路，可视化接口在这一层做数据聚合与格式归一化，而不是让前端承担多市场数据差异的转换。
- **多市场适配放在接口层**：70+ 国家市场的证券数据在字段和格式上存在差异，如果让每个图表组件各自处理，前端会积累大量条件分支。把归一化收在接口层，前端消费统一结构，代价是接口层的转换逻辑需要单独维护和测试。

## 关键难点

### 难点一：大数据量下的图表渲染

**问题**：单个视图可能承载数千个量化因子的结果，直接全量渲染会导致首屏卡顿和交互掉帧。

**方案**：在数据侧做分页与聚合，前端按视口需要增量渲染，避免一次性把全部数据点交给图表库。

**取舍**：为什么不在前端做全量数据的虚拟化？虚拟化能减少 DOM 节点，但数据本身仍在主线程解析和计算，大数据量下主线程依然会被占满。把裁剪前置到接口层，前端拿到的就是已收敛的数据量，渲染和交互都更稳定。代价是接口需要理解“视口需要多少数据”，接口与视图的耦合比纯前端裁剪更紧。

**结果**：首屏渲染不再被全量数据阻塞，因子切换和图表交互保持可响应。

### 难点二：多市场数据格式差异

**问题**：不同国家市场的证券数据在字段命名、空值表示、时间格式上不一致，同一套图表组件直接消费原始数据会渲染异常或展示错误。

**方案**：在接口层建立归一化层，把各市场数据映射为统一的内部结构，图表组件只消费归一化后的字段。

**取舍**：为什么不在前端用适配器模式逐个组件处理？组件级适配会让每个新图表重复实现一遍转换逻辑，且差异散落在前端各处难以排查。归一化收口到接口层，新增图表组件不需要关心市场差异。代价是接口层承担了更多职责，需要更严格的契约测试防止归一化规则回归。

**结果**：图表组件在多市场数据下表现一致，新增市场时前端无需改动。
