## 背景与目标

面向户外及运动爱好者的同城活动组局与交易平台，解决“想运动找不到搭子”的痛点。用户发布活动、他人报名参与，活动名额有限，涉及报名与支付的完整交易闭环。

目标是在微信小程序生态内跑通核心业务：登录、活动发布、报名、取消，并保证并发报名场景下的数据一致性。

## 我的角色与范围

独立全栈开发。从需求设计、架构搭建、前后端开发到 CI 配置全部由我完成，技术栈为 pnpm Monorepo 组织前端 Taro + React + Zustand、后端 NestJS + Prisma + MySQL。

## 技术栈与架构取舍

- **前端**：Taro + React + Zustand。选 Taro 而非原生小程序，是因为需要同一套业务逻辑未来复用到 H5；选 Zustand 而非 Redux，是因为状态规模不大，Zustand 的样板代码更少，且能直接在小程序多实例环境下按需订阅。
- **后端**：NestJS + Prisma + MySQL。选 NestJS 的模块化结构承载活动、报名、支付三个领域的边界；选 Prisma 而非 TypeORM，是因为报名防超卖涉及事务和行锁，Prisma 的交互式事务 API 能更直观地表达“事务内先查后改”的语义。
- **工程化**：pnpm Monorepo 统一前后端依赖与类型定义，GitHub Actions 跑 CI。

## 关键难点

### 难点一：高并发报名防超卖

**问题**：活动名额有限，多人同时点击报名时，如果先查余量再扣减，两个请求可能同时读到“还有 1 个名额”，都执行扣减，导致超卖。

**方案**：后端在数据库交互式事务中，用 `SELECT ... FOR UPDATE` 对活动行加排他锁，把“查余量→校验→扣减”三步锁在同一个事务里串行执行；同时给报名表加 `(活动ID, 用户ID)` 唯一索引，兜底防止同一用户重复报名。

**取舍**：为什么不用乐观锁（版本号 CAS）？报名场景写多读少、冲突概率相对可控，但用户点击报名的体验要求“要么成功要么明确失败”，乐观锁冲突后需要重试逻辑，用户侧可能出现“点了没反应”的中间态。行锁把冲突挡在数据库层，业务代码只处理“成功”和“名额已满”两种明确结果，前端交互更简单。代价是锁持有期间其他请求排队，但单个活动报名的事务极短（毫秒级），排队时间可接受。

**结果**：并发报名下不超卖，名额状态与报名记录保持一致；唯一索引保证同一用户不会重复占名额。

### 难点二：Custom TabBar 多实例状态不同步

**问题**：微信小程序的自定义 TabBar 在多个页面实例中各自维护一份状态，切换页面后，某个页面里 TabBar 的选中态或未读标记不更新，用户看到的是旧状态。

**方案**：改造 `Taro.eventCenter` 事件总线，在 TabBar 状态变更时广播事件，各页面实例订阅并同步自己的状态。

**取舍**：为什么不用全局状态库（如 Zustand）直接管理 TabBar？Taro 的多实例环境下，每个页面是独立的 React 渲染树，全局 store 的订阅在页面销毁时如果没正确清理，会积累内存泄漏；事件总线的订阅生命周期与页面实例绑定，`useEffect` 的清理函数里取消订阅即可，边界更清晰。代价是事件总线需要严格管理订阅/取消订阅的配对，否则会重复触发。

**结果**：切换页面后 TabBar 状态一致，未读标记和选中态实时同步。
